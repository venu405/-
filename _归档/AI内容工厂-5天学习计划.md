## 第 2 天：流量判断引擎（Phase 1 核心）

### 新知识点（今天重点）
| 概念 | 一句话 | 类比 |
|------|--------|------|
| **virality 评分** | `日均播放 ÷ 频道中位数日均播放`——修正版公式，时间归一化 + 抗 outlier | 比身高看"同龄人百分位"而非绝对值 |
| **outlier 检测** | 评分超过阈值（2×）标记为爆款 | 成绩单里明显高出平均的那几门 |
| **数据源抽象** | `TrendingDataSource` 协议，YouTube/TikTok 实现同一接口 | 插座：换插头不换电器 |
| **quota 概念** | YouTube API 按次计额度（10000/天），`search.list` 一次烧 100 | 话费流量包，别用最贵的套餐 |

**为什么修正公式**（二轮审查 P-1）：老视频发布久播放多，直接播放÷均值会误判——除以天数得到"日均"，再除以中位数（抗单个爆款拉高均值）。

### 动手任务
1. 建 `services/trending/__init__.py` + `base.py`（协议）+ `youtube.py`（YouTube 实现，暂留 TODO）+ `mock.py`（假数据源）
2. 在 `models.py`（或新 `trending_models.py`）按蓝图 11.4 建 `VideoMetrics` / `Outlier`
3. 写评分 + outlier 纯函数
4. 用 mock 数据验证：造 10 条视频（含 2 条明显爆款）→ 评分排序 → outlier 正确标出

### 验收标准
- [ ] mock 数据下：老视频（发布久）不会被误判爆款（时间归一化生效）
- [ ] 同一频道均值被爆款拉高时，中位数仍稳定（抗 outlier 生效）
- [ ] `TrendingDataSource` 接口能同时被 mock 和（未来）YouTube 实现

### 面试弹药（D2 收获）
> "评分用纯数学：日均播放 ÷ 频道中位数日均播放。**为什么不用 LLM 判断流量？** LLM 是概率模型，评分必须可复现、可解释——数学公式两行代码就能讲清楚，而且天然支持 outlier 阈值检测。LLM 只用在 AI 归因环节（解释为什么爆），**判断和归因分层**。"

## 第 3 天：选题提炼 + 脚本生成（Phase 2）

### 新知识点
| 概念 | 说明 |
|------|------|
| **评审前移**（P-7 修正） | 先评审选题"值不值得做"→ 通过才搜索/提炼，省 API 费 |
| **脚本 JSON 分镜** | `{title, hook, scenes:[{scene_description, scene_search_keywords_en, narration, duration}]}` |
| **英文检索词**（P-3 修正） | Pexels 检索中文效果差，脚本里带英文关键词 |
| **JSON 解析兜底复用** | 直接用 `planner.py` 的 `_extract_json_payload`（LLM 输出不可信） |

### 动手任务
1. 建 3 个 Agent（复用 `_create_tool_aware_agent` 工厂）：
   - 选题评审 Agent（打分，不合格不发下游）
   - 提炼 Agent（搜索 Tavily + 提炼核心看点）
   - 脚本 Agent（输出 JSON 分镜）
2. 脚本 Agent 的 prompt 里明确"只输出 JSON"（照抄 MPT 的 prompt 结构）
3. 复用 `_extract_json_payload` 解析脚本输出（验证：LLM 输出夹带废话也能解析成功）

### 验收标准
- [ ] 一个热点 → 输出完整 JSON 脚本（含英文检索词）
- [ ] 解析函数对"夹带说明文字的 JSON"仍能正确提取
- [ ] 评审不通过的选题不会进入下游（日志可验证）

### 面试弹药（D3 收获）
> "流水线加了质量关卡：选题先过评审 Agent 打分，不合格不发往下游——**每一层 LLM 调用都有成本，关卡越靠前越省钱**。脚本生成复用了我原有的 JSON 解析兜底链，因为 LLM 输出不可信，必须把'夹带废话的 JSON'解析成结构化数据。"

## 第 4 天：生产流水线（Phase 3）

### 新知识点
| 概念 | 说明 |
|------|------|
| **工程化拼接** | 不用文生视频模型，用"素材库 + TTS + FFmpeg"拼出稳定可用的视频 |
| **dispatch_material_search** | 照抄 `dispatch_search` 模式：Pexels 当搜索后端，带 notices + 缓存 |
| **edge-tts** | 微软免费 TTS，`zh-CN-XiaoxiaoNeural` 中文女声 |
| **FFmpeg 统一转码**（P-5 修正） | 素材编码/分辨率/采样率归一后再合成，防失败 |
| **降级链**（P-4 修正） | edge-tts 失败 → 重试 → Azure → 无配音+字幕兜底 |

### 动手任务
1. `dispatch_material_search`（Pexels 版，复用缓存/notices 模式）
2. edge-tts 配音：遍历 scenes，逐场景生成 MP3
3. FFmpeg 合成：竖屏 1080x1920，视频+配音+字幕+BGM
4. 文字模式：文章 Agent 直接输出 Markdown（可选，先保视频）

### 验收标准
- [ ] 一个脚本 JSON → 输出可播放的 30-60 秒竖屏 MP4
- [ ] 素材检索失败有 notices 且能降级（本地素材兜底）
- [ ] 配音失败走降级链（重试/无配音模式）不中断

### 面试弹药（D4 收获）
> "视频生成我选了**工程化拼接**而不是文生视频 API：素材库（Pexels）+ 免费 TTS（edge-tts）+ FFmpeg 合成，每段可替换、可降级、成本趋近于零。**工程化拼接比端到端生成更稳、更快落地**——这是 MoneyPrinterTurbo 验证过的 2026 主流路线。每条降级链都沿用了我项目的容错铁律：体验可降级，结果不能丢。"

## 📦 通用操作手册

```bash
pip install google-api-python-client   # YouTube 官方 API
pip install edge-tts                   # 免费配音

# 系统工具（Windows：choco install ffmpeg；或去 ffmpeg.org 下载加入 PATH）

```

### 每天铁律
1. **先备份再动手**（`cp file file.bak`，沿用老习惯）
2. **一次只做一个模块** → 验证 → 再下一个
3. **mock 优先**：不配 YouTube/Pexels Key 也能开发（数据源抽象的好处）
4. 每阶段结束**背出当天面试弹药**

### 风险预防表
| 坑 | 预防 |
|----|------|
| YouTube quota 爆 | 禁用 search.list（100/次）；频道结果 24h 缓存；开发用 mock |
| 素材中文检索差 | 脚本带 `scene_search_keywords_en` 英文词 |
| FFmpeg 合成失败 | 统一转码预处理（编码/分辨率/采样率归一） |
| edge-tts 连不上 | 降级链：重试 → Azure → 无配音+字幕 |
| 评分误判老视频 | 修正公式（日均 ÷ 中位数），必须用修正版 |
