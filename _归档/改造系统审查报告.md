## 一、按项目审查

### 项目 1：并发限流（Semaphore）

**现状**：`semaphore = Semaphore(self.config.max_concurrent_workers)`（=5），`guarded_worker` 包一层 `with semaphore`。

#### 发现的问题

| # | 问题 | 严重度 | 具体改进建议 | 优先级 |
|---|------|--------|--------------|--------|
| 1-1 | **限流粒度在"任务级"而非"请求级"**：Semaphore 只限制同时执行的任务数（5），但每个任务内部还有搜索调用 + LLM 流式调用，且多轮研究后每任务多次调用。瞬时 API 请求 = 并发任务数 × 每任务调用数，Semaphore(5) 挡不住请求峰值 | 高 | 限流下沉到"每次 API 调用"：在 `dispatch_search` 和 LLM 调用点各加一个请求级信号量（或共用一把），任务级限流保留为"队列管理" | P1 |
| 1-2 | **排队中的任务无任何反馈**：worker 在 `with semaphore` 处阻塞等待时，不发任何事件，前端任务一直显示 pending，用户不知道"是在排队还是卡了" | 中 | worker 进闸门前先 yield 一个 `task_status: queued`（或 status 消息"正在排队等待执行"），前端显示"排队中"徽章 | P2 |
| 1-3 | **单一并发数不区分 API 类型**：Tavily（官方高限流）和 DuckDuckGo（反爬敏感）共用一个配置，换搜索源后需手动调 | 低 | 拆分为 `max_concurrent_search` / `max_concurrent_llm`，或文档注明切换搜索源时同步调整 | P2 |

#### 用户体验评估
- ✅ 限流对用户透明（正常情况无感知）
- ❌ 排队任务无可见状态（1-2）；前端未显示"当前并发上限"信息
- ✅ 已完成百分比（completedTasks/totalTasks）反馈良好

### 项目 2：搜索缓存（KV + TTL）

**现状**：进程内 dict，key=`backend:fetch_full_page:query`，TTL=600s，容量 100 满则全清。验证：2.24s→0.00s。

#### 发现的问题

| # | 问题 | 严重度 | 具体改进建议 | 优先级 |
|---|------|--------|--------------|--------|
| 2-1 | **缓存毒化（cache poisoning）**：搜索 API 返回**空结果**（未抛异常）时，空结果也会被缓存 600 秒——期间所有相同查询持续拿到空结果，且不触发"降级为模型知识"的分支 | 高 | **空结果不缓存**；或失败结果用短 TTL（如 30s）缓存，用于防"缓存击穿"（同一查询并发涌来时只打一次 API） | P0 |
| 2-2 | **容量策略"满则全清"过于粗暴**：到 100 条时全部失效 → 命中率骤降 → 短时间内所有查询重新打 API（请求风暴 + 成本） | 中 | 用 `collections.OrderedDict` 实现 LRU（淘汰最久未用），或随机淘汰 1 条；全清是最差策略 | P1 |
| 2-3 | **TTL 固定 600s 一刀切**：快变信息（"最新进展"）10 分钟已过时，慢变信息（"发展史"）浪费重搜 | 中 | 关键词启发式 TTL：含"最新/2025/今天"→ 短 TTL（60s）；含"历史/原理/发展史"→ 长 TTL（1h） | P1 |
| 2-4 | **无可观测性**：没有命中率/缓存条数/过期次数统计，无法量化改造成果、无法判断 TTL 是否合理 | 中 | 加计数器（命中/未命中/淘汰），logger 定期输出命中率；面试汇报有数据支撑 | P1 |
| 2-5 | **进程内缓存限制**：多进程（uvicorn --workers N）不共享、重启丢失 | 低 | 单机单进程可接受；生产升级 Redis（set EX/get），逻辑不变——已知局限，文档注明即可 | P2 |

#### 用户体验评估
- ✅ 缓存透明，命中后秒回（用户感知 = 变快）
- ❌ 无"来自缓存"标识——可在来源区显示"（缓存 · 10 分钟内）"增强可信
- ✅ 不缓存时行为与原来完全一致（无回归）

### 项目 3：任务级重新生成

**现状**：`POST /research/regenerate`（收 topic+task_id+tasks 全量数据）+ 前端按钮。验证：只重跑目标任务，新总结进报告。

#### 发现的问题

| # | 问题 | 严重度 | 具体改进建议 | 优先级 |
|---|------|--------|--------------|--------|
| 3-1 | **每次重生成传输全量任务数据**：N 个任务 × 几千字 summary = 每次请求传几万字，带宽浪费 + 前端组装耗时；且**前端字段不完整**（notices/toolCalls/stream_token 未传回），后端重建的任务状态缺失 | 高 | 后端维护"最近一次研究"的内存会话（dict 缓存 topic→state），前端只传 task_id；同时补全前端传回字段 | P1 |
| 3-2 | **报告笔记未同步**：`regenerate_task` 未调用 `_persist_final_report`，若用户开启笔记，界面报告已更新但笔记文件还是旧的（数据不一致） | 中 | regenerate 完成后调用 `_persist_final_report(state, report)` 更新/创建结论笔记（`note_tool` 启用时） | P1 |
| 3-3 | **重生成无独立加载态**：全局 `loading` 锁导致重生成期间"开始研究"按钮也被禁用（可接受），但按钮文字不变，用户不知道"正在重新生成" | 中 | 按钮禁用时文字变"重新生成中…"，报告更新后触发 reportHighlight（代码里已有 pulse 机制，复用） | P2 |
| 3-4 | **降级信息不提示**：若目标任务重生成时搜索失败（降级为模型知识），前端无任何提示，用户误以为结果是搜索来的 | 中 | 透传 notices 到前端任务详情（现有 notices 机制已有，补上即可） | P2 |
| 3-5 | **接口无鉴权**：任何人可调 POST /research/regenerate | 低 | 单机学习项目可接受；生产需加 API Key/登录态 | P2 |

#### 用户体验评估
- ✅ "只重做不满意任务"的交互价值高，符合直觉
- ❌ 按钮无进行中文案（3-3）；报告更新无高亮提示（3-3）
- ❌ 左侧任务列表无快捷"重新生成"入口（需先进详情）——可接受，详情页已够
- ✅ 任务状态、打字机、来源更新均复用主流程，体验一致

### 项目 4：多轮研究

**现状**：`_execute_task` 内循环（最多 `max_web_research_loops`=3 轮），每轮搜索+总结，缺口评估驱动换查询词，轮次总结拼接。验证：3 轮全跑，总结 14182 字。

#### 发现的问题

| # | 问题 | 严重度 | 具体改进建议 | 优先级 |
|---|------|--------|--------------|--------|
| 4-1 | **成本显著膨胀且用户无选择权**：3 轮 ×（搜索+总结）+ 评估调用，实测单任务 83.8s；5 个任务并发 = 用户等很久 + API 费用翻倍，但前端没有"研究深度"选项 | 高 | 前端提供"研究深度"选择（快速=1轮/标准=2轮/深度=3轮），作为参数传给后端覆盖配置；同时显示预计耗时 | P0 |
| 4-2 | **每轮总结互相隔离**：第 2 轮总结只基于第 2 轮搜索结果，不知道第 1 轮已说了什么；最终是简单拼接（\n\n.join），轮次间无递进整合，内容可能重复/矛盾 | 中 | 把前几轮总结作为上下文注入本轮总结 prompt（累积上下文），让后轮"补充"而非"重写" | P1 |
| 4-3 | **缺口评估只看"本轮"总结**（agent.py:481 `round_text`）：评估员不知道累计内容，可能补搜"第 1 轮已覆盖"的缺口（重复轮次） | 中 | 传给 `_assess_gap` 的应是**累计总结**（round_summaries 拼接），而非单轮 | P0 |
| 4-4 | **前端无轮次感知**：多轮总结 14000+ 字全部累加到任务 summary 区，无分轮/折叠，阅读困难、渲染压力 | 中 | 前端按轮次分节展示（"第 1 轮…第 2 轮…"），或总结区加折叠 | P2 |
| 4-5 | **固定轮数上限是硬成本墙**：即使用户只想要"快速查一下"，系统仍可能跑满 3 轮 | 低 | 由 4-1 的深度选择解决；或"信息足够即收敛"的判定放宽（checklist 已部分解决） | P2 |

#### 用户体验评估
- ✅ 多轮让报告更全（三轮聚合 14182 字），深度明显提升
- ❌ 无深度选择（4-1）、无轮次指示（4-4）、长总结无折叠（4-4）
- ❌ 时间线有"第 N 轮补充研究"状态（status 事件），但任务详情无明确"当前第几轮"标识
- ⚠️ 成本/等待时间随轮数线性增长，用户无感知无控制

### 项目 5：checklist 结构化评估

**现状**：`_build_checklist`（意图→子问题）+ `_assess_gap`（checklist 逐项核对，拆解失败降级整体判断，解析失败收敛）。验证：稳定触发 3 轮。

#### 发现的问题

| # | 问题 | 严重度 | 具体改进建议 | 优先级 |
|---|------|--------|--------------|--------|
| 5-1 | **checklist 每轮重复拆解**（agent.py:558）：`_assess_gap` 每次调用都重新 `_build_checklist(task.intent)`，同一任务最多拆 2 次——同一意图拆出的子问题可能不一致（LLM 随机性），浪费 2 次 LLM 调用 + 增加延迟 | 高 | **任务开始时拆一次，多轮复用**：`_execute_task` 里拆一次存入局部变量传给 `_assess_gap`（或缓存到 task 对象）；预估省 2 次 LLM 调用/任务 | P0 |
| 5-2 | **解析失败默认收敛 = 丢信息**：prompt 要求"逐项输出已覆盖/未覆盖 + NO_GAP 或 JSON"，但解析只查 `NO_GAP in response` 和 `{}`。若 LLM 输出"1.已覆盖 2.未覆盖…"却没输出 JSON/NO_GAP → 解析失败 → `return (False, None)` **静默丢弃真实缺口**。"整体二选一"时代这个兜底合理（防死循环），checklist 时代它成了丢信息的漏洞 | 高 | 解析失败时改为**保守补搜**（返回 True + 上次 query 变体）或**重新评估一次**；只有当"明确 NO_GAP"才收敛。防死循环仍由轮数上限保证 | P0 |
| 5-3 | **子问题过长导致评估 prompt 膨胀**：实测拆出的子问题每个 30+ 字（含完整描述），6 个 = 200+ 字注入评估 prompt，token 成本上升 | 中 | 拆解 prompt 限制"每个子问题 ≤ 20 字、3-5 个"；评估 prompt 里总结截断 3000 字符可保留 | P1 |
| 5-4 | **gap 描述未利用**：JSON 里 `gap`（未覆盖项简述）与 `query` 分离，gap 被丢弃——gap 信息能提升 query 检索质量 | 低 | 用 gap 修饰 query（如 `f"{gap} {query}"`）或至少记入 notices 给用户看"还缺什么" | P2 |
| 5-5 | **评估成本无上限控制**：checklist（拆解）+ 评估 = 每轮 2 次 LLM，3 轮最多 6 次评估相关调用——与 4-1 成本问题叠加 | 中 | 由 5-1（复用 checklist）+ 4-1（深度选择）共同缓解 | P1 |

#### 用户体验评估
- ✅ 内部机制，无直接 UI 影响
- ❌ 间接影响：评估调用增加延迟与成本（5-1/5-5）
- ✅ 对用户的价值 = 报告更全（多轮更可靠触发）

## 二、跨项目总结

### 共性问题归纳（6 条）

1. **可观测性全面缺失**：5 个改造都没有指标/日志统计（缓存命中率、轮次数、并发等待时长、评估耗时、降级次数）——无法量化成果、无法诊断问题、面试缺数据。→ 全局加结构化日志/计数器。
2. **成本控制靠"默认"不靠"设计"**：多轮（3 轮）+ checklist（每轮 2 次评估）叠加，单任务成本/延迟翻数倍，但用户无深度选择、无成本预期。→ 前端深度选择 + 默认收敛策略优化。
3. **降级与异常大多"静默"**：缓存空结果、评估解析失败收敛、搜索降级为模型知识——都有兜底但用户无感知，可能误以为结果是"新鲜的/搜索来的"。→ 降级信息统一透传前端 notices。
4. **无状态设计的一致性代价**：regenerate 传回全量数据、进程内缓存、内存会话缺失——全部假设"单机单进程单用户"。学习项目可接受，但**架构文档应注明升级路径**（Redis、会话管理、鉴权）。
5. **前端交互滞后于后端能力**：后端已支持多轮/深度/事件流，但前端无深度选择、无轮次分节、长总结无折叠、排队无提示、报告更新无高亮。→ 一轮前端体验迭代。
6. **安全基线部分完成**：.gitignore 已补（key 防提交）✓；但 Tavily key 曾在对话中出现，建议重新生成轮换；接口无鉴权（单机可接受）。

### 推荐实施顺序

| 优先级 | 事项 | 对应问题 | 理由 |
|--------|------|----------|------|
| **P0-1** | checklist 任务级复用（拆一次、多轮用） | 5-1 | 省 2 次 LLM/任务，成本与延迟立减，改动小 |
| **P0-2** | 评估解析失败改为"保守补搜" | 5-2 | 当前可能静默丢缺口 = 正确性问题 |
| **P0-3** | 缺口评估改用**累计总结** | 4-3 | 防重复补搜，避免轮次浪费 |
| **P0-4** | 缓存**空结果不缓存**（或短 TTL） | 2-1 | 防缓存毒化，正确性问题 |
| P1-1 | 前端"研究深度"选择（1/2/3 轮） | 4-1 | 成本/体验的核心控制点 |
| P1-2 | 限流粒度下沉到请求级 | 1-1 | 多轮后请求峰值防不住 |
| P1-3 | regenerate 同步报告笔记 | 3-2 | 数据一致性 |
| P1-4 | 缓存 LRU 淘汰 + 命中率日志 | 2-2/2-4 | 稳定性 + 可观测性 |
| P1-5 | 每轮总结注入前轮上下文 | 4-2 | 总结质量递进 |
| P2 | 排队提示、按钮文案/报告高亮、轮次分节/折叠、gap 透传、子问题限长、笔记字段补全 | 1-2/3-3/3-4/4-4/5-3/5-4 | 体验打磨 |

## 三、审查结论

**总体评价**：5 项改造功能全部可用、验证充分（这是基础分），核心问题集中在**成本控制、正确性兜底策略、可观测性和前端体验**四个维度。

**最优先的两件事**（影响正确性）：
1. 评估解析失败默认收敛 → 改为保守补搜（5-2）
2. 空结果缓存 → 不缓存或短 TTL（2-1）

**最划算的一件事**（成本立减）：checklist 任务级复用（5-1）——一行改动级别，省一半评估调用。

**最有价值的一件事**（用户体验）：前端研究深度选择（4-1）——把成本控制权交给用户。

> 建议：P0 四项可安排为"第 4.5 天"（约 1-2 小时），P1 作为"第 5 天联调"的一部分，P2 视时间取舍。每项修复后按既有流程验证（备份 → 改 → 语法检查 → 重启 → 实测）。
