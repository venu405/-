## 一、目标架构总览

### 1.1 架构图（详见上方可视化）

```
【入库链路 · 离线】
企业文档源(PDF/Word/MD/网页/DB)
  → 解析与预处理（pdfplumber / python-docx / trafilatura / SQL）
  → 清洗与分块（去噪 + 重叠窗口，元数据挂载）
  → 内容向量化（Embedding 服务）
  → 向量数据库（Qdrant/pgvector，元数据：kb_id / 权限标签 / 文档指纹）

【问答链路 · 实时】
用户提问（Vue3 前端）
  → API 网关（FastAPI，身份认证 + SSE）
  → 权限过滤（用户身份 → 检索过滤条件）
  → 查询重写（多轮上下文理解）
  → 混合检索（向量 + BM25，带权限过滤，读取向量库）
  → 重排 Rerank（bge-reranker / 交叉编码器）
  → 问答编排 Agent（复用多 Agent 架构 + 引用溯源）
  → 答案 + 引用（chunk→文档映射标注）
  → SSE 流式返回（复用现有事件通道）
  → 前端渲染（打字机 + 来源链接）

【横切能力】
权限管控（RBAC + 文档级标签 + 知识库级隔离）
反馈闭环（点赞/点踩 → 记录 → 定期评估 → 调优）
质量评估（RAGAS 离线评测 + 在线监控指标）
增量更新（文档指纹比对 + 定时扫描 + 事件驱动）
```

### 1.2 核心模块职责划分（输入 → 输出）

| 模块 | 职责 | 输入 → 输出 |
|------|------|-------------|
| **ingest_service**（文档接入） | 接收上传/导入，识别格式，调度解析 | 文件流 → 原始文本 + 元数据 |
| **parser**（解析器） | 各格式专用解析 | PDF/Word/MD/HTML/DB 行 → 纯文本 |
| **cleaner + chunker**（清洗分块） | 去噪、去页眉页脚、固定/语义分块、重叠 | 原始文本 → 带元数据的 chunk 列表 |
| **embedding_client**（向量化） | 调 embedding 模型，批量化 + 增量 | chunk → 向量 |
| **vector_store**（向量存储检索） | 写入、查询、元数据过滤、删除 | 向量+元数据 → 相似度命中列表 |
| **retriever**（检索器） | 混合检索（向量 + BM25）融合 | 查询向量 → 候选 chunk（Top-K） |
| **reranker**（重排） | 交叉编码器精排 | Top-50 候选 → Top-5 精排 |
| **orchestrator**（问答编排） | 查询重写、检索增强生成、引用标注、流式输出 | 用户问题 + 上下文 → 带引用的流式答案 |
| **auth_service**（权限） | 认证、RBAC、过滤条件生成 | 请求 + 用户身份 → 允许的 kb_id/标签集合 |
| **session_manager**（会话） | 多轮历史存储、摘要压缩 | 会话 ID + 轮次 → 上下文窗口 |
| **feedback_service**（反馈） | 记录点赞/点踩、错误报告 | 会话 ID + 评价 → 评估数据库 |

## 二、技术选型建议（含优劣势与适用场景）

### 2.1 向量数据库

| 方案 | 优势 | 劣势 | 适用场景 | 推荐度 |
|------|------|------|----------|--------|
| **Qdrant** | 元数据过滤强、Rust 高性能、部署简单（单二进制/镜像）、支持 payload 过滤实现权限隔离 | 需单独部署（或嵌入式模式）| **企业单机→分布式平滑升级** | ⭐⭐⭐⭐⭐ 首选 |
| **pgvector** | Postgres 插件，与业务数据同库、事务一致 | 千万级向量性能弱于专用库；混合检索需配合 tsvector | 中小规模、已有 PG 的团队 | ⭐⭐⭐⭐ 稳妥 |
| **Milvus** | 亿级向量、分布式、GPU 加速 | 部署运维重（依赖 etcd/minio）| 大规模生产（千万+）| ⭐⭐⭐ |
| **Chroma** | 轻量、原型快、纯本地 | 生产功能弱（过滤/并发/备份）| 快速 Demo | ⭐⭐ |
| **Elasticsearch** | 已有 ES 可复用；kNN + BM25 原生混合 | 向量性能一般、license 成本 | 已深度使用 ES 的团队 | ⭐⭐⭐ |

**决策建议**：
- **起步（MVP）**：`pgvector`（零新增基础设施，与后续用户/权限表同库）或 `Qdrant`（独立部署但能力最全）
- **规模化**：Qdrant（推荐）或 Milvus（亿级才需要）
- 本方案下文以 **Qdrant** 为主选、pgvector 为备选

### 2.2 嵌入模型（Embedding）

| 模型 | 优势 | 劣势 | 合规/部署 | 推荐度 |
|------|------|------|-----------|--------|
| **BGE-M3**（BAAI） | 中文强、多语言、1024 维、稀疏+稠密+多向量，**可本地部署** | 需一定显存（可 CPU 运行） | ✅ 私有化 | ⭐⭐⭐⭐⭐ 首选 |
| **text-embedding-3-small/large** | 质量稳定、生态好 | **数据出境**（发 OpenAI）、按量计费 | ⚠️ 需合规评估 | ⭐⭐⭐⭐ |
| **智谱 embedding-3** | 中文优、国内 API | 按量计费、数据入第三方 | ⚠️ 国内合规可 | ⭐⭐⭐ |
| **Ollama 本地模型**（nomic-embed-text/bge 系列） | 完全本地、免费、开箱 | 质量略逊 BGE-M3 | ✅ 私有化首选 | ⭐⭐⭐⭐ |

**决策建议**：
- 数据不出境要求 → **BGE-M3 本地部署**（推荐，与私有化路线一致）
- 无合规压力 → text-embedding-3 或智谱 API 更快上手
- **接口抽象**：`embedding_client` 统一封装，切换模型只改配置（沿用项目"配置化"铁律）

### 2.3 RAG 框架

| 方案 | 优势 | 劣势 | 推荐度 |
|------|------|------|--------|
| **自研（推荐）** | 复用现有多 Agent/SSE/缓存架构；可控、可讲、面试价值高 | 解析器/分块器需自己接 | ⭐⭐⭐⭐⭐ |
| **LlamaIndex** | 解析/分块/索引最成熟，可当"库"用 | 编排层与现有架构重叠 | ⭐⭐⭐⭐ 借库不借框架 |
| **LangChain** | 生态大、组件全 | 抽象重、黑盒、版本变动大 | ⭐⭐⭐ |
| **Haystack** | 生产管线友好 | 社区小于前两者 | ⭐⭐⭐ |
| **RAGFlow** | 开箱即用、带 UI | 黑盒、难定制、难讲清 | ⭐⭐ |

**决策建议**：**自研编排 + 借力组件库**——用 LlamaIndex 的 `loaders`/`text_splitter` 作为库引入（解决解析分块），编排层完全自研（复用 run_stream 模式）。理由：你的核心竞争力（SSE + 多 Agent + 缓存 + 限流）全部在自研层，引入重框架等于推倒重来。

### 2.4 重排模型（Rerank）

| 方案 | 说明 | 适用 |
|------|------|------|
| **bge-reranker-v2-m3** | 本地部署、中文强 | 私有化首选 |
| **Cohere Rerank** | API 即用、质量高 | 无合规压力 |
| **交叉编码器自训** | 用反馈数据微调 | 后期优化（Phase 4）|

### 2.5 技术选型汇总（推荐组合）

```
向量库：Qdrant（备选 pgvector）
Embedding：BGE-M3 本地（备选 API）
解析分块：LlamaIndex loaders/text_splitter（当库用）
重排：bge-reranker-v2-m3 本地
编排：自研（复用现有 run_stream / 多 Agent）
LLM：现有 DeepSeek（生成）——注意：检索链路独立于生成模型
```

## 三、数据接入与权限设计

### 3.1 企业常见格式接入方案

| 格式 | 解析方案 | 工具 | 注意事项 |
|------|----------|------|----------|
| **PDF** | 文本提取 + 表格还原 | `pypdf` / `pdfplumber`（表格）/ `PyMuPDF`（扫描件 OCR 需配 tesseract） | 扫描版 PDF 需 OCR；双栏排版需布局分析 |
| **Word** | 段落 + 表格提取 | `python-docx` | 处理 .docx；.doc 旧格式需转换（LibreOffice） |
| **Markdown** | 保留标题层级做分块边界 | 内置 `markdown-it` / 正则 | 标题是天然分块锚点（父子分块） |
| **网页** | 正文抽取（去导航/广告） | `trafilatura`（最佳）/ `BeautifulSoup` | 动态渲染页面需 playwright 渲染 |
| **数据库** | 表 → 行/字段级 chunk | SQL 查询 + 模板化文本 | 每行转"字段:值"文本；敏感字段入库前脱敏 |

**统一元数据 schema**（所有格式入库时必须携带，权限与溯源都靠它）：

```json
{
  "kb_id": "kb-001",
  "doc_id": "doc-9f3a",
  "title": "采购制度 V3",
  "doc_type": "pdf",
  "author": "行政部",
  "uploaded_at": "2026-08-06T10:00:00Z",
  "fingerprint": "sha256:xxxx",          // 增量更新比对用
  "permissions": {"visibility": "internal", "teams": ["finance", "admin"]},
  "source_url": "https://..."            // 溯源链接（网页/DB 场景）
}
```

### 3.2 权限模型（两级）

```
第一级 · 知识库级隔离（租户隔离，最粗粒度）：
  每个知识库 = Qdrant 中的一个 collection 或 payload 中的 kb_id 命名空间
  用户 → 可访问的 kb_id 列表（RBAC 表）
  检索时强制 `payload["kb_id"] IN (用户可访问列表)`

第二级 · 文档级过滤（细粒度）：
  文档 metadata.permissions 声明可见范围
  检索时额外叠加 `payload["visibility"] = "public" OR payload["teams"] CONTAINS 用户团队`
```

**数据隔离策略（三选一，推荐 A）**：

| 策略 | 实现 | 适用 | 优缺 |
|------|------|------|------|
| **A. 单库 + 元数据过滤（推荐）** | 所有文档进一个 collection，检索时按权限过滤 | 中小规模、团队级 | 简单；过滤条件多时性能略降 |
| B. 每知识库独立 collection | 一个 kb 一个 collection | 大规模、强隔离要求 | 隔离彻底；跨库检索复杂 |
| C. 物理隔离（独立实例） | 每个租户一套服务 | 金融/涉密 | 最安全；成本最高 |

**检索过滤流程（伪代码，权限在检索前强制，绝不在生成后补救）：**

```python
def search(user, query, kb_id):
    allowed = auth_service.allowed_kbs(user)          # ① 用户 → 可访问库
    if kb_id not in allowed:
        raise Forbidden                                # ② 库级校验
    filter_cond = {
        "must": [
            {"key": "kb_id", "match": {"value": kb_id}},
            {"should": [                                 # ③ 文档级过滤
                {"key": "visibility", "match": {"value": "public"}},
                {"key": "teams", "match": {"any": user.teams}},
            ]},
        ]
    }
    hits = vector_store.search(query_vector, filter=filter_cond, top_k=50)
    return reranker.rerank(hits, query)[:5]              # ④ 精排
```

## 四、问答质量保障设计

### 4.1 多轮对话上下文管理

```
方案：查询重写（Query Rewriting）——不直接把"上一轮的原始问题"塞给检索，而是独立调一次 LLM 把"本轮问题 + 历史"改写成自包含的检索查询：

prompt = "用户历史：...\n本轮问题：...\n请将本轮问题改写成独立可检索的查询，只输出查询词"

流程：会话历史（session_manager）→ 重写 → 检索 → 生成
```

- 会话历史用**滑动窗口 + 摘要压缩**（超过 N 轮把早期对话压缩成摘要，防上下文膨胀——复用你项目 `max_web_research_loops` 的"收敛"思想）

### 4.2 回答引用溯源

```
答案生成时要求 LLM 按 chunk 编号引用：
  "根据《采购制度》第 3.2 节[1]，超过 5 万元的采购需招投标[2]"

结构化输出：答案文本 + citations 列表
citations: [{chunk_id, doc_id, title, snippet, source_url}]

前端渲染：把 [1][2] 变成可点击的悬浮卡片（复用现有 sources 事件机制 + parseSources 的解析思路）
```

**复用点**：你项目的 `sources` 事件（`latest_sources` + `raw_context`）和 `task_summary_chunk` 打字机机制**原样可用**——引用列表 = sources 事件的变体，答案 = task_summary_chunk 的变体。

### 4.3 答案准确性评估

**离线评估（发布前，必须做）**：
- 建 50-100 条评测集（真实业务问题 + 标准答案 + 期望引用的文档）
- 用 **RAGAS** 指标打分：
  - `faithfulness`（忠实度）：答案是否都基于检索内容（防幻觉）
  - `answer_relevance`（相关性）：答案是否回答用户问题
  - `context_precision`（检索精度）：检索到的 chunk 是否有效
- 每次改分块参数/重排/提示词后跑回归，分数不能掉

**在线监控（运行中）**：
| 指标 | 含义 | 阈值告警 |
|------|------|----------|
| 无引用率 | 答案没带引用的比例 | > 10% 告警 |
| 拒答率 | "知识库中未找到"的比例 | 过高 → 库覆盖不足 |
| 反馈率 | 用户点踩比例 | > 5% 告警 |
| 检索延迟 p95 | 检索耗时 | > 1s 告警 |

### 4.4 基于反馈的持续优化闭环

```
用户点赞/点踩（前端按钮）
  → feedback_service 记录（会话 ID + 问题 + 答案 + 引用 + 评价）
  → 定期（每周）导出：
      ① 点踩样本 → 人工/LLM 分析失败原因（检索漏了？重排错了？幻觉？）
      ② 归因 → 调整对应环节（分块大小 / 重排阈值 / 提示词 / 补文档）
  → 跑 RAGAS 回归 → 通过才发布
```

## 六、扩展性与可维护性设计

### 6.1 多知识库

- **命名空间隔离**：每个 kb 一个 `kb_id`，Qdrant payload 强制过滤（或独立 collection）
- **跨库检索**：Phase 3 之后支持多 kb 并查（用户有权限的全部库），结果按相关度融合
- **库管理**：kb 的创建/授权/停用走 auth_service 统一管理

### 6.2 高并发

| 手段 | 实现 |
|------|------|
| 异步任务队列 | 入库走 ARQ/Celery worker（不阻塞 API）；问答仍走同步 SSE |
| 限流 | 复用现有 Semaphore 配置化模式：LLM 并发 / 检索并发 / 入库并发分开限 |
| 缓存 | 检索结果缓存（复用 `_search_cache` 模式，key = 查询+权限集+kb）；embedding 结果缓存（同 query 不重复算） |
| 连接池 | 向量库/LLM 客户端连接池化（httpx 复用现有 client） |
| 水平扩展 | Qdrant 可分布式；API 层无状态（会话存 Redis）可多副本 |

### 6.3 增量更新

```
文档指纹（sha256）比对：
  定时扫描（或 webhook 触发）→ 计算新文档指纹
    → 新指纹 → 入库
    → 指纹变化 → 删旧 chunk + 重新向量化
    → 指纹相同 → 跳过（零成本）
```

### 6.4 私有化部署（企业交付关键）

```
docker-compose 架构：
  api（FastAPI 容器，现项目镜像化）
  qdrant（向量库容器）
  embedding（BGE-M3 推理服务容器，GPU 可选）
  ollama（本地 LLM，可选：DeepSeek 本地版 或 保持云端 API）
  postgres（业务表：用户/权限/反馈/文档元数据）
  nginx（反代 + HTTPS 终结）
```

**离线模型矩阵**：Embedding=BGE-M3（本地）、生成=DeepSeek API 或 Ollama 本地模型（按合规要求切换，`embedding_client` 与 `_init_llm` 已配置化，切换只改 .env）。

### 6.5 可维护性铁律（沿用项目已有实践）

1. 一切外部依赖配置化（.env）——已证明可行
2. 模块边界清晰：ingest / retrieval / generation / auth 互不越界
3. 全链路日志 + 指标（复用 `_cache_stats` 的日志模式，扩展命中率/延迟/反馈率）
4. 每个阶段留评测集做回归（防"改坏了不知道"）

## 七、关键决策点与风险

### 7.1 需要你拍板的决策点

| 决策点 | 选项 | 我的建议 |
|--------|------|----------|
| 向量库 | Qdrant / pgvector | 有合规/简洁偏好选 Qdrant；想少装东西选 pgvector |
| 数据是否出境 | 本地 BGE-M3 / 云端 API | 企业默认按"不出境"设计，选 BGE-M3 |
| 生成模型 | DeepSeek API / Ollama 本地 | 先 API（快），私有化阶段再本地化 |
| 前端形态 | 改造现有 App.vue / 新增对话页 | 新增独立视图组件，保留研究功能（可加"研究/问答"双模式） |

### 7.2 风险表

| 风险 | 等级 | 缓解 |
|------|------|------|
| 检索质量差（用户问不到答案） | 高 | Phase 2 混合检索 + 重排 + RAGAS 门槛；反馈闭环持续调 |
| 权限泄露（越权检索） | 高 | 过滤在检索层强制（非生成后补救）+ 渗透测试验收项 |
| 幻觉（答非所问/编造） | 高 | faithfulness 评估门槛 + 强制引用 + 无引用告警 |
| 数据出境合规 | 中 | 默认本地 embedding；生成模型按合规切换 |
| 增量更新丢数据 | 中 | 指纹比对 + 删除前先验证新 chunk 入库成功 |
| 成本失控（embedding 重复计算） | 低 | embedding 缓存 + 增量更新（不变不重算） |

## 八、与现有能力的衔接说明（面试弹药）

> "我在深度研究项目基础上规划了企业级 RAG 演进：**入库链路**（文档解析→清洗分块→向量化→Qdrant 存储，元数据携带权限标签）与**问答链路**（认证→权限过滤→查询重写→混合检索+重排→复用现有多 Agent 架构生成带引用的流式答案）双线并行。**大量复用现有资产**——SSE 事件通道、多 Agent 工厂、KV+TTL+LRU 缓存、Semaphore 配置化限流，只新增 ingest/retrieval/auth/session 等横向模块。质量保障用 RAGAS 离线评测 + 无引用率/反馈率在线监控形成闭环。分四阶段落地：MVP（2 周）→ 质量增强（2 周）→ 权限多租户（1.5 周）→ 规模化私有化（2 周），每阶段有明确验收标准。关键取舍：编排层自研（复用现有架构）而非引入 LangChain，向量库选 Qdrant（元数据过滤强 + 可平滑扩容）。"
