# 项目改造蓝图与技术决策

> 基于 helloagents-deepresearch（FastAPI + Vue3 + SSE + 多 Agent）的工程化改造蓝图
> 版本 v1.0 ｜ 2026-08-11 ｜ 交付物 ①：改造蓝图 + 关键技术决策

## 一、现状深度分析

### 1.1 技术栈与代码规模（实测）

| 层 | 技术 | 备注 |
|----|------|------|
| 后端 | FastAPI 0.141 + uvicorn | 单进程，4 个接口 |
| LLM | hello-agents 0.2.9（OpenAI 兼容）+ DeepSeek | 统一封装于 `_init_llm` |
| 搜索 | Tavily（可插拔 SearchTool） | 配置化切换 |
| 前端 | Vue 3.5 + Vite 6 + TS + axios | 单页 App |
| 流式 | SSE（自研解析） | 事件协议 `data: {json}\n\n` |

代码规模：**backend/src 共 2293 行**（agent.py ~600、services/ 8 个文件、models/config/prompts/utils）。

### 1.2 现有接口（main.py，4 个）

```
GET  /healthz            健康检查
POST /research           非流式研究（返回完整报告）
POST /research/stream    SSE 流式研究（主流程）
POST /research/regenerate 任务级重新生成
```

### 1.3 核心功能清单（改造基线）

1. **多 Agent 协作**：规划/总结/报告/摘要/对比/主编 + 工厂模式隔离
2. **SSE 流式**：事件通道（status/todo_list/sources/task_summary_chunk/final_report/done）
3. **并发执行**：Thread + Queue 生产者-消费者 + Semaphore 配置化限流
4. **多轮研究**：checklist 结构化缺口评估 + 收敛控制
5. **搜索缓存**：KV + TTL + LRU + 命中率日志
6. **任务级重新生成**：复用 `_execute_task` 增量更新

### 1.4 架构亮点（保留，不破坏）

| 亮点 | 价值 |
|------|------|
| 生成器驱动的事件流（run_stream） | SSE 天然契合，代码可读性高 |
| 工厂模式 + 清历史 | 并发任务隔离，防串话 |
| 配置化铁律 | 一切外部依赖 .env 可控 |
| 多级降级链 | 搜索失败→模型知识；流式失败→非流式兜底 |

### 1.5 工程化短板（本次改造要解决的硬伤）

| # | 短板 | 严重度 | 现状证据 |
|---|------|--------|----------|
| 1 | **零测试** | 🔴 最高 | backend 无 tests/ 目录，无 pytest 依赖 |
| 2 | **零 CI/CD** | 🔴 高 | 无 GitHub Actions，改代码靠人工验证 |
| 3 | **错误处理分散** | 🔴 高 | 依赖 try/except 散落，无统一异常层 |
| 4 | **日志非结构化** | 🟡 中 | 只有 `logger.info` 文本，无 request_id 贯穿 |
| 5 | **配置单层** | 🟡 中 | 仅 .env + from_env，无分层/校验提示 |
| 6 | **无 Docker 化** | 🟡 中 | 启动靠手敲 uvicorn 命令 |
| 7 | **无持久化** | 🟡 中 | 任务状态只存内存，重启即丢 |
| 8 | **无可观测性** | 🟡 中 | 仅有缓存命中率日志，无指标端点 |

## 二、开源蓝本调研与筛选

### 2.1 调研范围（2026-08 实测数据）

| 候选 | Stars | 定位 | 与本项目的相关性 |
|------|-------|------|------------------|
| **full-stack-fastapi-template**（tiangolo） | 18k+ | FastAPI 工程化官方模板 | ⭐⭐⭐⭐⭐ 工程化同栈 |
| **LangGraph** | 24k+（v1.0） | 生产级 Agent 状态图框架 | ⭐⭐⭐⭐⭐ 架构同源 |
| **Dify** | 151k+ | LLMOps 平台（工作流/RAG/可观测） | ⭐⭐⭐⭐ 产品化 |
| **RAGFlow** | 79k+ | 深度文档理解 RAG 引擎 | ⭐⭐⭐ RAG 专项 |
| OpenAI Agents SDK | 新（Swarm 继任） | handoffs 多 Agent | ⭐⭐⭐ 但 OpenAI 锁定 |
| CrewAI | 52k+ | 角色化团队 Agent | ⭐⭐ 编排控制弱 |

### 2.2 筛选结论：三个改造蓝本

| 蓝本 | 借鉴维度 | 核心可借鉴点 |
|------|----------|-------------|
| **① full-stack-fastapi-template** | 工程化基建 | pytest 测试结构、GitHub Actions CI/CD、Docker Compose 双环境、配置分层、JWT 认证骨架 |
| **② LangGraph** | Agent 架构 | 状态图（node/edge/reducer）、**checkpoint 持久化**（断点续跑）、HITL interrupt、time-travel 回放、LangSmith 可观测思想 |
| **③ Dify** | 产品化 | 工作流 DSL 版本化、**LLMOps 可观测**（日志/标注/反馈闭环）、插件市场模式、模块边界约束（import-linter）、企业功能（RBAC/审计） |

**关键血统关系（面试故事点）**：
> 本项目 `models.py` 中 `Annotated[list, operator.add]` 就是 **LangGraph 的 reducer 风格注解**——项目本身从 LangGraph 模板移植而来（第 14 章教程背景）。改造时"先研究 LangGraph 的生产级设计（checkpoint/HITL/observability），再以自研方式补进自己的手写编排"——这是最有说服力的故事：**不是换框架，而是把框架的思想吸收进自己的架构**。

### 2.3 明确不借鉴（决策依据）

| 方案 | 为什么不用 |
|------|-----------|
| 直接引入 LangGraph 重写 | 现有手写编排已能工作且被精读掌握；重写推倒重来，且面试时"手写 vs 框架"对比本身就是加分项 |
| 引入 OpenAI Agents SDK | 项目用 DeepSeek（非 OpenAI），SDK 价值在 OpenAI 生态 |
| 整套引入 Dify | 那是产品不是代码库，黑盒；只借鉴其工程化/可观测/插件思想 |

## 三、改造方案

### 3.1 需重构的模块

| 模块 | 现状问题 | 改造方向 |
|------|----------|----------|
| **main.py** | 无统一异常处理、无请求 ID | 加异常中间件 + request_id + 结构化日志 + 错误响应规范 |
| **agent.py** | `_execute_task` 单点降级逻辑分散 | 抽出统一 `run_with_fallback` 装饰器；事件生成加 schema 校验 |
| **config.py** | 单层 .env | 分层：默认值 → .env → .env.local（本地覆盖），加载失败给清晰提示 |
| **services/search.py** | 缓存/限流/日志混在一个模块 | 拆出 `cache.py`（通用 KV+TTL+LRU 可复用组件）；保留对外 API 不变 |
| **前端 App.vue** | 单文件 ~1000 行，无状态管理 | 拆组件（SearchForm/TaskList/ReportViewer/FeedbackBar）；错误态统一 |
| **（新增）infra/** | — | 新增：Dockerfile、docker-compose.yml、.github/workflows/ci.yml、tests/ |

### 3.2 可借鉴的设计模式（从蓝本映射到本项目）

| 蓝本模式 | 本项目落地 | 改造位置 |
|----------|-----------|----------|
| **state graph + reducer**（LangGraph） | 把 run_stream 的"状态机"显式化：State 流转 + 事件类型枚举 | models.py / agent.py |
| **checkpoint 持久化**（LangGraph） | 任务状态（todo_items/各任务 summary/轮次）快照到 SQLite，重启可恢复 | 新增 persistence.py |
| **HITL interrupt**（LangGraph） | 研究阶段间插入"确认点"（可选：人工确认后再生成报告） | agent.py 事件流 |
| **time-travel 回放**（LangGraph） | SSE 事件持久化 + 重放接口（/research/{id}/replay） | 新增 replay 模块 |
| **pytest 三层结构**（fastapi-template） | tests/unit + tests/integration + tests/e2e，mock LLM 层 | 新增 tests/ |
| **CI 流水线**（fastapi-template） | lint（ruff）→ test（pytest）→ build（前端）→ 镜像构建 | .github/workflows |
| **LLMOps 可观测**（Dify） | 每次研究的指标事件：LLM 调用数/token/轮次/命中率/耗时 | 新增 metrics 模块 |
| **工作流 DSL**（Dify） | 把"研究配置"（深度/并发/搜索源/是否多轮）序列化为可复用的研究配置 JSON | 新增 research_spec.py |
| **插件式工具注册**（Dify 插件市场） | 现有 ToolRegistry 升级为装饰器注册（`@tool("web_search")`） | 改造 notes.py 工具注册 |
| **模块边界约束**（Dify import-linter） | 引入 `import-linter` 强制 services 层不 import 表示层 | 工程配置 |

### 3.3 应补充的功能特性

| 特性 | 说明 | 优先级 |
|------|------|--------|
| **统一错误处理** | FastAPI 异常处理器 + SSE 错误事件（type:"error" 已存在，补 schema） | P0 |
| **结构化日志** | loguru 或 structlog，`request_id` 贯穿 + JSON 格式 | P0 |
| **测试体系** | pytest + pytest-asyncio + httpx AsyncClient；**mock LLM/搜索层**（关键：测试不花 API 钱） | P0 |
| **CI/CD** | GitHub Actions：lint → test → build；master 合并触发 | P1 |
| **Docker 化** | backend Dockerfile + docker-compose（api + 前端 nginx） | P1 |
| **配置分层** | defaults → .env → .env.local，缺失 key 启动即报错（fail-fast） | P1 |
| **任务持久化** | 研究快照 SQLite：重启/崩溃可断点续跑（checkpoint 思想） | P2 |
| **可观测端点** | `/metrics` 返回：缓存命中率、LLM 调用数、平均耗时、失败率 | P2 |
| **事件重放** | 已结束研究的 SSE 事件流可回放（time-travel 简化版） | P2 |
| **反馈闭环** | 前端报告区"👍/👎 + 原因"，落库供统计 | P3 |
| **Webhook 通知** | 研究完成/失败回调（企业集成场景） | P3 |

### 3.4 差异化亮点设计（面试独特性来源）

1. **"手写编排 + LangGraph 思想"双轨叙事**：能现场讲清"为什么不用框架、框架的 checkpoint/HITL 思想怎么用手写实现"——这是绝大多数候选人没有的深度
2. **研究配置 DSL（research_spec）**：把一次研究的完整配置（主题/深度/并发/搜索源/多轮开关）序列化为 JSON，可保存/分享/复跑——产品级功能
3. **断点续跑**：任务中途崩溃，重启后从 checkpoint 恢复（不重复已完成的搜索，省钱）
4. **成本可观测面板**：每次研究统计 token 消耗/API 调用次数/耗时（可扩展为月度成本报表）
5. **SSE 事件 schema 化**：事件类型用 Pydantic 模型定义 + 校验，前后端契约化（事件即 API）
6. **mock 驱动的确定性测试**：LLM/搜索全部 mock，测试毫秒级完成且可复现——演示"可测试的 Agent 系统"

## 四、关键技术决策说明

### 决策 1：手写编排 vs 引入 LangGraph —— **保留手写 + 吸收思想**

| | 手写（现状） | 引入 LangGraph |
|--|-------------|---------------|
| 代码归属感 | ✅ 每一行都懂 | ❌ 黑盒 |
| 面试讲深度 | ✅ "为什么不用框架" | ⚠️ 只能讲框架 |
| 改造风险 | 低（增量） | 高（重写） |
| checkpoint/HITL | 自研 200 行以内 | 现成 |

**结论**：保留手写，用 3.2 节的模式映射补 checkpoint 等能力。面试话术："我研究过 LangGraph 的生产级设计，它用 checkpoint 解决崩溃恢复、用 reducer 解决状态合并。我在自己的手写编排里用 SQLite 快照实现了等价的断点续跑，并保留了事件流架构——因为我的核心资产是 SSE 流式 + 工厂隔离，换框架会丢掉这些。"

### 决策 2：日志方案 —— **loguru（或 structlog）**

- 理由：项目已有 loguru 依赖（pyproject 里已声明）；配置简单、开箱 JSON 输出
- 落地：`request_id` 用 contextvar 贯穿；每个事件打一条结构化日志

### 决策 3：持久化存储 —— **SQLite（零依赖）**

- 场景：单机学习/面试项目，checkpoint 数据量小
- 理由：不需要引入 Redis/PG；`sqlite3` 标准库 + 一个表搞定
- 未来：生产化时切 Redis（接口抽象好，`PersistenceBackend` 协议）

### 决策 4：CI —— **GitHub Actions**

- 理由：免费、与 GitHub 仓库一体化、模板成熟
- 流水线：`ruff lint → pytest（mock 模式）→ 前端 vue-tsc + build →（可选）docker build`

### 决策 5：可观测性 —— **自研轻量 metrics，不接 LangSmith**

- 理由：LangSmith 与手写架构集成成本高且收费；自研 `/metrics` + 结构化事件日志足够面试展示
- 演进：后续可接 OpenTelemetry（OTel 标准协议，metrics 模块预留 exporter 接口）

### 决策 6：测试策略 —— **mock 掉 LLM 与搜索，测逻辑不测模型**

- `tests/mocks/` 提供 FakeLLM（返回固定 JSON/流式 chunk）和 FakeSearchTool（返回固定结果）
- 好处：测试快（毫秒级）、免费、可复现、CI 可跑
- 保留 1-2 个"真集成"测试标记 `@pytest.mark.integration`（需 .env key，CI 跳过）

## 五、改造后目标架构（文字版）

```
backend/
├── app/
│   ├── main.py              # 路由 + 异常中间件 + request_id
│   ├── core/                # config 分层、logging、exceptions
│   ├── agents/              # agent.py 拆出：orchestrator / executor / gap_evals
│   ├── services/            # planner / summarizer / reporter / search / notes
│   ├── persistence/         # checkpoint（SQLite）、replay
│   ├── metrics/             # 指标采集 + /metrics
│   └── schemas/             # SSE 事件 Pydantic 模型（事件契约）
├── tests/
│   ├── unit/                # 纯逻辑（解析/分块/缓存）
│   ├── integration/         # 带 mock 的全流程
│   └── e2e/                 # 真实 API（httpx AsyncClient）
├── Dockerfile
├── docker-compose.yml
└── .github/workflows/ci.yml
```

**改造原则**：**增量而非重写**——现有 2293 行代码的架构资产（事件流/工厂/缓存/限流）全部保留，围绕它"补壳"（测试/CI/日志/错误处理/持久化/可观测）。这符合你"改过、跑过、能讲细节"的简历原则。
