## 一、工作量总览与优先级矩阵

| 优先级 | 阶段 | 内容 | 预估工作量 | 面试价值 |
|--------|------|------|-----------|----------|
| **P0** | Phase 1 | 测试体系 + 错误处理 + 结构化日志 | 4-5 人日 | ⭐⭐⭐⭐⭐ 补最大硬伤 |
| **P1** | Phase 2 | CI/CD + Docker + 配置分层 | 3-4 人日 | ⭐⭐⭐⭐ 工程化闭环 |
| **P2** | Phase 3 | 断点续跑 + 可观测端点 + 事件重放 | 4-5 人日 | ⭐⭐⭐⭐⭐ 差异化 |
| **P3** | Phase 4 | 反馈闭环 + Webhook + 插件注册 | 3-4 人日 | ⭐⭐⭐ 产品化加分 |

**排序逻辑**：先补"被面试官一眼看穿的硬伤"（零测试/零CI），再做"别人没有的亮点"（断点续跑/可观测）。每阶段独立可交付、可验收，阶段间不阻塞。

## 二、Phase 1：测试体系 + 错误处理 + 日志（P0，4-5 人日）

### 目标
让项目从"零测试、裸奔式错误处理"变成"有 20+ 测试覆盖核心链路、错误有统一出口、日志可追踪"。

### 任务分解

| # | 任务 | 具体动作 | 验收标准 |
|---|------|----------|----------|
| 1.1 | 搭建测试骨架 | 建 `tests/` 目录；加 pytest/pytest-asyncio/httpx 依赖；建 `tests/conftest.py` 提供 app fixture | `pytest` 命令可运行 |
| 1.2 | Mock 层 | 建 `tests/mocks/fake_llm.py`（流式 chunk + 完整返回）与 `fake_search.py`（固定结果）；用依赖注入替换 `_init_llm` / `dispatch_search` | 不依赖真实 API，测试零成本 |
| 1.3 | 单元测试 | 覆盖：`_extract_json_payload`（planner）、`strip_thinking_tokens`（utils）、缓存命中/过期/LRU（search）、checklist 解析失败降级（agent） | ≥ 10 个用例，含边界（空响应/乱输出） |
| 1.4 | 集成测试 | `run_stream` 全流程：mock 后断言事件序列 `todo_list → sources → chunk → final_report → done`；`regenerate` 只重跑目标任务 | 2 条主链路各 1 个用例通过 |
| 1.5 | API 测试 | httpx AsyncClient 调 `/healthz`、`/research/stream`（带 mock） | 4 个接口全部有测试 |
| 1.6 | 统一异常处理 | FastAPI 全局异常处理器（HTTP/业务/未知 → 统一 JSON 错误体）；SSE 流内异常 → `{"type":"error","detail":...}`（已有基础，补 schema 与日志） | 抛错时返回规范错误体，日志记录 traceback |
| 1.7 | 结构化日志 | 配置 loguru：JSON 输出 + `request_id`（contextvar 贯穿请求） | 日志可 grep request_id 串起一次研究全链路 |

### 阶段验收（全部满足才算过）
- [ ] `pytest` 全绿（≥20 用例），单次运行 < 60 秒
- [ ] 不配置 .env key 也能跑完整个测试套件（mock 生效证明）
- [ ] 制造一次搜索失败：前端收到 `error` 事件，日志可追踪完整链路

### 面试弹药（Phase 1 后）
> "我给项目补了完整测试体系：用 mock 层隔离 LLM 和搜索——FakeLLM 返回固定流式 chunk，测试毫秒级完成且不花 API 钱。核心断言是事件序列契约：todo_list → sources → chunk → final_report → done，任何破坏 SSE 协议的改动都会在 CI 里当场失败。另外用 request_id 贯穿一次研究的全部日志，排查问题从'看输出猜'变成'按 ID 拉全链路'。"

## 三、Phase 2：CI/CD + Docker + 配置分层（P1，3-4 人日）

### 目标
"本地能跑" → "push 到 GitHub 自动检查，一条命令部署"。

### 任务分解

| # | 任务 | 具体动作 | 验收标准 |
|---|------|----------|----------|
| 2.1 | ruff lint 配置 | pyproject 已含 ruff 配置；补 `ruff check .` 进 CI | 本地 ruff 通过 |
| 2.2 | GitHub Actions | `.github/workflows/ci.yml`：`ruff → pytest → vue-tsc → vite build` | 推分支触发，全绿 |
| 2.3 | backend Dockerfile | 多阶段构建（依赖层缓存）；`uvicorn app.main:app` | `docker build` 成功 |
| 2.4 | docker-compose | `api` 服务 + 前端静态托管（nginx）；`.env.example` 完整示例 | `docker compose up` 一键起服务 |
| 2.5 | 配置分层 | `config.py` 三级：Pydantic 默认 → .env → .env.local（gitignore）；缺失必填项启动报错 | 无 .env 启动有明确错误提示 |
| 2.6 | 安全基线 | `.gitignore` 确认 .env/.env.local；secret 扫描进 CI（可选 gitleaks） | 无 key 被提交 |

### 阶段验收
- [ ] GitHub 仓库 push → Actions 自动跑全绿（可截图存档）
- [ ] `docker compose up` 一条命令起服务，浏览器可访问
- [ ] 删除 .env 后启动，错误信息指出缺失的 key

### 面试弹药（Phase 2 后）
> "我配了 GitHub Actions CI：每次 push 自动跑 lint、测试、前端类型检查和构建，任何回归在合并前就被拦截。Docker 多阶段构建 + Compose 一键部署，从'手敲命令启动'变成'一条命令拉起整个服务'。配置做了 fail-fast 分层：缺 key 启动即报错，绝不带病运行。"

## 四、Phase 3：断点续跑 + 可观测端点 + 事件重放（P2，4-5 人日）

### 目标
做出**别人没有的差异化能力**——吸收 LangGraph checkpoint / time-travel 思想的自研实现。

### 任务分解

| # | 任务 | 具体动作 | 验收标准 |
|---|------|----------|----------|
| 3.1 | 持久化模块 | `persistence.py`：SQLite 表 `research_runs(id, spec_json, checkpoint_json, status, created_at)`；`PersistenceBackend` 接口（未来可换 Redis） | 单测：save/load 往返一致 |
| 3.2 | 断点写入 | `run_stream` 每完成一个任务写一次 checkpoint（todo_items 状态 + 各任务 summary + 轮次）；加 `run_id` 参数 | 任务 3/5 时 kill 进程，重启可从任务 4 继续 |
| 3.3 | 续跑接口 | `POST /research/stream` 支持 `run_id`：命中 checkpoint 则跳过已完成任务 | 续跑不重复已完成任务的搜索（省 API 可验证） |
| 3.4 | 指标采集 | `metrics.py`：请求数/成功率/平均耗时/缓存命中率/LLM 调用数（复用现有 `_cache_stats`）；`GET /metrics` 返回 JSON | 连续跑 2 次研究，指标可观测到缓存命中提升 |
| 3.5 | 事件重放 | SSE 事件落盘（append 到 run 记录）；`GET /research/{run_id}/replay` 重放事件流 | 前端可回看历史研究过程 |
| 3.6 | 研究配置 DSL | `research_spec.py`：研究配置序列化 JSON（主题/深度/并发/搜索源/多轮），`POST /research/specs` 保存可复用 | 保存配置 → 用配置复跑，行为一致 |

### 阶段验收
- [ ] kill 进程实验：任务进行中杀后端 → 重启 → 续跑成功且不重跑已完成任务
- [ ] `/metrics` 返回 6+ 指标，两次同主题研究命中率从 0 升到 >0
- [ ] 历史研究可回放（前端可见完整事件流）

### 面试弹药（Phase 3 后，本阶段是面试主角）
> "我研究了 LangGraph 的生产级设计后，在自己的手写编排里实现了等价的断点续跑：任务状态每完成一步就 checkpoint 到 SQLite，进程崩溃后重启能从未完成的任务继续——不会重复已经花钱的搜索。研究配置序列化成 DSL 可保存复跑；SSE 事件落盘支持历史回放（time-travel 的简化版）。这些不是框架给的，是我理解状态机思想后自己实现的——这比'用了 LangGraph'更能说明深度。"

## 六、实施建议与注意事项

### 6.1 顺序铁律
1. **每阶段独立完成并验收后再进入下一阶段**，避免"半拉子工程"
2. **先备份再动手**（沿用你之前的 `.bak` 习惯）
3. **测试先行**：Phase 1 的测试套件会成为后续所有阶段的"安全带"——Phase 3 改 agent.py 时跑一遍测试就知道有没有破坏契约

### 6.2 常见坑
| 坑 | 预防 |
|----|------|
| mock 不到位导致测试真调 API | conftest 里全局强制替换 `dispatch_search` 与 LLM，测试内禁用网络 |
| SSE 测试超时 | 用 `asyncio.wait_for` 包 `StreamingResponse` 迭代 |
| checkpoint 与代码版本不兼容 | checkpoint 带 `schema_version` 字段，升级时迁移或丢弃 |
| CI 环境缺系统依赖（如 OCR） | 测试不依赖真实解析，解析器单测用内存文本 |

### 6.3 面试表达总纲（四阶段合一）
> "改造分四步：先补测试与错误处理（mock 驱动、事件契约断言、request_id 全链路日志）→ 再上 CI/CD 与 Docker（push 自动检查、一键部署、配置 fail-fast）→ 然后做差异化能力（checkpoint 断点续跑、/metrics 可观测、事件回放、研究配置 DSL）→ 最后产品化（反馈闭环、Webhook、插件化工具注册）。改造全程增量进行，2293 行核心代码的事件流架构、工厂隔离、缓存限流全部保留——我做的是补壳，不是重写。"
