## 二、每日详细计划

### 第 1 天：限制并发数（agent.py）

**目标**：目前所有子任务"同时开线程跑"（`for task in state.todo_items: Thread(...).start()`），改成最多同时 3 个。

**学习目标**
- 理解 `Semaphore`（信号量）：限流闸门，`acquire()` 拿票（没票就等）、`release()` 还票
- 理解为什么限流：DuckDuckGo/LLM API 都有速率限制，5 个任务同时打 API 容易触发限流/超时

**动手步骤**
1. 备份：`cp agent.py agent.py.bak`
2. `agent.py` 顶部加 `from threading import Semaphore`
3. 在 `threads: list[Thread] = []` 附近加：`semaphore = Semaphore(3)`
4. 包一层守卫函数（原 worker 不动）：
```python
def guarded_worker(task, step):
    with semaphore:          # 拿票，满了就排队等
        worker(task, step)   # 原来的 worker 逻辑不变

for task in state.todo_items:
    thread = Thread(target=guarded_worker, args=(task, step), daemon=True)
    threads.append(thread)
    thread.start()
```

**验收标准**
- 重启后端，跑一次研究（3-5 个任务），确认任务状态能正常走完 in_progress → completed
- 观察前端：任务不是"全部同时开始"，而是最多 3 个在进行中
- 把 `Semaphore(3)` 改成 `Semaphore(1)`，应看到任务变串行（验证限流生效）

**面试弹药**
> "我把并发线程限制为最多 3 个，用 `Semaphore` 实现——因为搜索和 LLM API 有速率限制，无限制并发会触发限流和超时。这也让系统在任务数很多时保持稳定。"

### 第 2 天：缓存搜索结果（search.py）

**目标**：同一查询词在短时间内重复出现时，直接返回上次结果，不重复调搜索 API。

**学习目标**
- 字典当缓存：`{查询词: 搜索结果}`
- 三个工程问题：① 缓存膨胀怎么办（设上限，超了就清）② 信息有时效怎么办（加时间戳 TTL）③ 缓存是进程内的，重启就丢（可接受）

**动手步骤**
1. 备份 `search.py`
2. 在文件顶部加模块级缓存：
```python
_search_cache: dict[str, dict] = {}        # {查询词: 结果}
_MAX_CACHE_SIZE = 100                      # 最多缓存 100 条
_CACHE_TTL_SECONDS = 600                   # 10 分钟过期
```
3. 在 `dispatch_search` 开头加命中检查，结尾写入缓存：
```python
def dispatch_search(query, config, loop_count):
    cache_key = f"{config.search_api}:{query}"     # key 带上后端名，防止混用
    hit = _search_cache.get(cache_key)
    if hit and (time.time() - hit["ts"]) < _CACHE_TTL_SECONDS:
        return hit["payload"], hit["notices"], hit["answer"], hit["backend"]
        # 命中！直接用上次结果（注意返回 4 个值要和原来一致）
    ...
    # 原本 return 的地方，改成先写缓存再 return
```
4. 写缓存时统一走一个 helper，顺带处理容量：
```python
def _put_cache(key, payload, notices, answer, backend):
    if len(_search_cache) >= _MAX_CACHE_SIZE:
        _search_cache.clear()              # 简单策略：满了全清（可接受）
    _search_cache[key] = {"ts": time.time(), "payload": payload,
                          "notices": notices, "answer": answer, "backend": backend}
```

**验收标准**
- 连续两次跑同一个主题的研究，第二次明显更快（搜索阶段直接命中）
- 加日志 `logger.info("Search cache HIT: %s", query)`，跑两次看到 HIT
- 改缓存 key 不带上 backend 会怎样？（ta 一个验证理解：不同后端结果混用）

**面试弹药**
> "我实现了进程内搜索缓存：以'后端+查询词'为 key，带 10 分钟 TTL 和容量上限。同一查询重复研究时直接命中缓存，省掉重复 API 调用，实测第二次研究明显提速。这就是 KV 缓存思想，生产环境可以平滑升级到 Redis。"

### 第 3 天：任务级"重新生成"（后端接口 + 前端按钮）

**目标**：报告生成后，用户可对**单个子任务**点"重新生成"，只重跑该任务的搜索+总结，然后报告用新总结更新。

**学习目标**
- 复用已有代码：`_execute_task(state, task, emit_stream=True)` 本来就是"单任务执行"——直接复用它
- 后端新接口（main.py 加一个 POST 接口，接收 task_id，返回 SSE 流）
- 前端按钮 + fetch 调用（复用 api.ts 的 SSE 解析函数）

**动手步骤（后端）**
1. 备份 main.py / agent.py
2. `agent.py` 加方法：
```python
def regenerate_task(self, topic: str, task_id: int) -> Iterator[dict]:
    state = SummaryState(research_topic=topic)
    # 找到目标任务（需要传入原任务列表，或前端把原任务数据传回来）
    task = <从传入数据重建 TodoItem>
    yield {"type": "status", "message": f"正在重新生成任务 {task_id}"}
    for event in self._execute_task(state, task, emit_stream=True, step=1):
        yield event
    # 重新生成报告（reporter 重新读所有任务）
    report = self.reporting.generate_report(state)
    yield {"type": "final_report", "report": report}
    yield {"type": "done"}
```
3. main.py 加接口 `POST /research/regenerate`（收 topic + task 数据 + task_id），用 `StreamingResponse` 包住上面的生成器
4. **注意**：重新生成后要把新总结回填到"原始研究"的状态里——最简单的方案是让前端把更新后的任务数据传回后端，或后端内部维护"最近一次研究的 state"

**动手步骤（前端）**
1. App.vue 每个任务卡片加 [重新生成] 按钮
2. 点击 → 调 `runResearchStream`（api.ts 已支持传 payload + onEvent，新增一个接口路径参数）
3. onEvent 里对 `task_summary_chunk` 更新对应任务（现有逻辑复用）→ `final_report` 更新报告区

**验收标准**
- 研究完成后，点任务 2 的"重新生成"，只有任务 2 重新搜索+打字机总结，任务 1/3 不动
- 报告区更新为新总结的版本
- 点重新生成时其他任务没有重新执行（观察前端时间线）

**面试弹药**
> "我实现了任务级重新生成：复用已有的 `_execute_task` 做单任务重跑，新增后端接口 + 前端按钮。用户不用整份报告重跑，只重做不满意的子任务——这是增量更新的思想（只重算变更部分）。"

### 第 4 天：多轮研究（agent.py + prompts.py）⭐ 压轴

**目标**：用上 `config.py` 里闲置的 `max_web_research_loops = 3`，实现"搜 → 总结 → 评估缺口 → 再搜"循环。

**学习目标**
- 循环控制：外层 for 循环包住"搜索+总结"，最多 N 轮
- 缺口评估：新加一段 prompt，让 Agent 判断"当前总结还缺什么信息"（或者更简单：比对子任务 intent 与总结，缺关键词就再搜）
- 终止条件：① 无缺口 ② 达到轮数上限 ③ 兜底（防止死循环）

**动手步骤（推荐入门版——不新增 Agent，复用总结 Agent）**
1. 备份 agent.py / prompts.py
2. prompts.py 加一段"缺口评估指令"（或直接复用 task_summarizer 的 prompt 后缀）
3. `_execute_task` 改造为循环：
```python
max_loops = self.config.max_web_research_loops   # 默认 3
for loop in range(max_loops):
    搜索(查询词) → 总结(上下文)
    if loop == 0:
        gap = 评估缺口(总结, task.intent)   # 用 LLM 判断还缺什么
        if 没有缺口: break
        查询词 = 基于缺口生成的新查询词
    # 第二轮起把上一轮的总结作为上下文一部分，追加新搜索结果
```
4. 状态里已有 `research_loop_count` 计数器，每轮 `+= 1`（锁保护）
5. `final_step`、步骤号等逻辑注意兼容（多轮时 step 编号）

**验收标准**
- 配置 `MAX_WEB_RESEARCH_LOOPS=2` 在 .env 里，跑一个主题，日志看到"第 1 轮搜索 / 第 2 轮搜索"
- 第二轮查询词与第一轮不同（基于缺口生成）
- 报告里总结比原来更全（多轮补充的信息进入总结）
- 改 `MAX_WEB_RESEARCH_LOOPS=1` 退化为单轮，验证配置生效

**面试弹药（压轴话术）**
> "我实现了多轮研究循环：项目预留了 `max_web_research_loops` 配置和轮数计数器，但主流程没有真正使用。我补全了它——每轮搜索总结后，让 Agent 基于任务意图评估信息缺口，有缺口就生成新查询词再搜，最多循环 N 轮，无缺口提前收敛。这就是 OpenAI Deep Research 的核心机制：多轮检索 + 缺口评估 + 收敛控制。"

## 五、风险与坑（提前打预防针）

| 改造 | 常见坑 | 预防 |
|------|--------|------|
| 限制并发 | Semaphore 用错位置（没包住 worker）→ 限流不生效 | 用 guarded_worker 包一层，不动原 worker |
| 缓存 | ① 缓存 key 不带 backend → 结果混用 ② 缓存永不失效 → 信息过时 ③ 忘返回 4 个值 → 解包报错 | key 带 backend、加 TTL、返回结构保持一致 |
| 任务级重生成 | ① 新总结没回填到原状态 → 报告还是旧的 ② 前端事件流没区分是"重生成"还是"全新研究" | 前端维护 activeTaskId，重生成事件复用同一套 onEvent |
| 多轮研究 | ① 死循环（缺口评估永远说有缺口）② 上下文无限膨胀（每轮都追加全文）③ 步骤号错乱 | 轮数上限硬限制、每轮只追加新摘要+缺口、step 编号与 loop 关联 |
| 所有改造 | 改多个文件一起验证 → 出 bug 不知道是谁的 | 一次只改一个功能，改完先验证再下一个 |
